**4. `account-delete` — ตัดสินใจแล้ว (2026-08-08) — ยังไม่ deploy ตัว cooldown ใหม่ตอนนี้**
ห้ามเปิด flow ที่สร้าง pending deletion ถ้า cron/email/deletion pipeline ยังไม่พร้อม — ต้อง deploy `account-delete` + `account-delete-cron` + SQL cooldown + transactional email ส่วนที่จำเป็น **เป็นชุดเดียวพร้อมกัน** หลัง dependency พร้อมและผ่าน Full Account Deletion Test เท่านั้น — ให้ Dispatch ทำ analysis/design/local prep ต่อ (ห้าม deploy/รัน SQL/แตะ production)

- **(a) Cooldown 7 วัน** (เปลี่ยนจากคำตอบเดิม):
  - ผู้ใช้ส่งคำขอลบบัญชี → เข้าสถานะ pending deletion
  - ภายใน 7 วันยกเลิกคำขอลบได้
  - ครบ 7 วันจึงลบถาวร
  - ออกแบบให้ปลอดภัย ป้องกันการลบผิดบัญชี
  - ⚠️ ถ้ามี behavior สำคัญที่ยังต้องตัดสินใจก่อนเขียนส่วนที่กระทบ flow จริง **ต้องรายงาน Lin ก่อน ห้ามเดาเอง**

- **(b) `payout_ledger`:**
  - ข้อมูลที่จบแล้ว (จ่ายแล้ว/ปฏิเสธแล้ว) **เก็บไว้ก่อน ห้ามลบ ห้าม anonymize เอง**
  - เรื่อง retention/จัดการระยะยาว ตัดสินใจภายหลัง

- **(c) แจ้งอีเมล:**
  - ยื่นคำขอลบบัญชี → ต้องส่งอีเมลแจ้งทันที
  - บอกว่าจะถูกลบถาวรเมื่อครบ 7 วัน + วิธียกเลิกคำขอภายในช่วงนั้น
  - ⚠️ ต้องตรวจระบบอีเมลที่มีอยู่ก่อนใช้ **ห้ามสร้างระบบใหม่โดยเดา**

- **(d) `star_ledger`:**
  - ต้องตรวจ schema + foreign key + โค้ดที่อ่าน/เขียนจริงก่อน ว่ามี PII หรือข้อมูลเชื่อมกลับไปหาผู้ใช้ไหม
  - **ยังไม่แก้/ลบข้อมูลใดๆ จนกว่าจะรายงานผลให้ Lin ตัดสินใจ**

> ขอบเขตรอบนี้: analysis/design/local preparation ทำได้ **ห้าม deploy, รัน SQL, หรือแตะ production** — ถ้า cooldown 7 วันต้องเปลี่ยน database schema/cron/scheduled job/deletion architecture ต้องหยุดตรงจุดนั้นก่อน แล้วสรุปสิ่งที่ต้องเปลี่ยนมาให้ Lin ตัดสินใจ

## D. Unlink Google/Email — บันทึกขัดแย้งกัน ต้องยืนยันครั้งสุดท้าย

**9. กฎการ unlink ผู้ให้บริการล็อกอิน — ปิดงาน (ยืนยันครั้งสุดท้ายแล้ว 2026-08-08)**

**กฎถาวร (คำตอบสุดท้าย ใช้ตัวนี้เท่านั้น กันเถียงซ้ำ):**
อนุญาตให้ Unlink ได้ทุกวิธี รวมถึงวิธีที่ใช้สมัครบัญชีครั้งแรก โดยมีเงื่อนไข:
- หลัง Unlink ต้องเหลืออย่างน้อย 1 authentication method ที่ผู้ใช้ Login กลับเข้าบัญชีเดิมได้จริง
- วิธีสมัครดั้งเดิมไม่มีสิทธิ์พิเศษ — unlink ได้ถ้ามีวิธีอื่นที่ใช้งานจริงเหลืออยู่
- synthetic/fake email หรือ identity ที่ Login จริงไม่ได้ (เช่นอีเมลปลอมของ LINE) **ห้ามนับเป็นช่องทางที่เหลือ**
- เหลือช่องทางเดียว → ห้าม Unlink ช่องทางนั้น

ตัวอย่าง: LINE+Google → unlink อันไหนก็ได้ · LINE อย่างเดียว → unlink LINE ไม่ได้ · LINE+synthetic email → unlink LINE ไม่ได้ (synthetic email ไม่นับเป็นช่องทางที่เหลือ)

**ตรงกับโค้ดที่มีอยู่แล้ว** (`account-unlink/index.ts` — ดูผลตรวจ B.5 ด้านบน) ไม่ต้องแก้โค้ดเพิ่มจากกฎนี้

> ⛔ **แต่ `account-unlink` ยังห้าม deploy** จนกว่า Mandatory Pre-Deploy Test B.5a/B.5b จะผ่าน เพื่อยืนยัน behavior กับ Supabase จริง (ดูข้อ 5 ในหัวข้อ B ด้านบน)
